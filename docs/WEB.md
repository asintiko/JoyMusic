# Веб-приложение (`@joymusic/web`)

Next.js 16 (App Router, React 19, Tailwind 4) в монорепозитории. Здесь живут три поверхности:

| Маршрут                          | Что это                                                                    |
| -------------------------------- | -------------------------------------------------------------------------- |
| `/v/[slug]`                      | гостевой PWA: цель QR-кода, экран «сейчас играет», поиск и заказ трека     |
| `/tv/[slug]`                     | экран для телевизора 16:9 в зале, без взаимодействия                       |
| `/`, `/ru`, `/en`                | лендинг (`docs/LANDING.md`), статические страницы                          |
| `/art?u=`                        | прокси обложек (только `dzcdn.net`, `mzstatic.com`, `deezer.com`, до 3 МБ) |
| `/v/[slug]/manifest.webmanifest` | манифест PWA конкретного заведения                                         |

Гость не входит в аккаунт. Все данные идут через контракт из `@joymusic/shared`: клиент `createApiClient`, `createRealtimeClient`, редьюсер `applyServerEvent`, `nowPlayingProgress` и `serverOffset`, словари статусов и подсказок. Руками `fetch` и `WebSocket` мы нигде не пишем.

## Запуск

```sh
pnpm --filter @joymusic/web dev          # порт 3000
pnpm --filter @joymusic/web build
pnpm --filter @joymusic/web start
pnpm --filter @joymusic/web typecheck    # next typegen + tsc
pnpm --filter @joymusic/web lint
pnpm --filter @joymusic/web test         # vitest
pnpm --filter @joymusic/web test:e2e     # Playwright, см. ниже
```

Чтобы посмотреть вживую, нужен API (`docs/API.md`, раздел «Запуск локально»). Демо-заведение `joy-demo-club` создаёт `db:seed`. Открыть `http://localhost:3000/v/joy-demo-club` и `http://localhost:3000/tv/joy-demo-club`. Токен стола лежит в админке QR (`?t=<token>`), без него страница работает так же, просто без учёта стола.

Чтобы оживить пустое заведение, есть скрипт `apps/web/scripts/demo-state.mjs`. Он входит как `dj@joymusic.uz`, стартует сессию, кладёт в очередь несколько реальных треков из каталога и включает первый:

```sh
API_URL=http://localhost:4000 node apps/web/scripts/demo-state.mjs
```

## Переменные окружения

Шаблон: `apps/web/.env.example`. Секретов нет.

| Переменная             | По умолчанию            | Назначение                                                                              |
| ---------------------- | ----------------------- | --------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_API_URL`  | `http://localhost:4000` | база API для браузера (HTTP и WebSocket). Вшивается при сборке                          |
| `API_URL`              | равна публичной         | база API для серверного рендера, если из контейнера web API виден по другому адресу     |
| `NEXT_PUBLIC_SITE_URL` | пусто                   | публичный origin сайта для QR на ТВ. Если пусто, берётся из заголовков запроса (`Host`) |

### CORS и прокси

Браузер ходит в API напрямую, поэтому у API в `CORS_ORIGINS` должен быть origin веб-приложения (`http://localhost:3000` уже в `.env.example` API). Тот же список API проверяет в заголовке `Origin` при подключении к WebSocket. Рерайт `/v1/*` через Next мы не делаем намеренно: прокси Next не проксирует WebSocket, а realtime здесь главная функция. Если нужен единый origin (Caddy или nginx), проксируйте `/v1/` на API целиком, включая апгрейд соединения, и задайте `NEXT_PUBLIC_API_URL` равным origin сайта.

Три корневых layout (route groups) нужны ради серверного рендера: тема заведения и язык попадают в `<html data-theme lang>` до первого кадра, без мигания.

### Гостевое приложение (`src/guest`)

| Файл                                          | Ответственность                                                                                   |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `session-store.ts`                            | анонимный `deviceId`, `guestJoin`, токен с обновлением по сроку и по 401, токен стола, скан QR    |
| `api.ts`                                      | ленивый клиент API (`@joymusic/shared` подгружается после гидратации) и обёртка с повтором по 401 |
| `use-venue-feed.ts`                           | снимок и события через realtime, оценка сдвига серверных часов, переподключение, resync           |
| `live-state.ts`                               | редьюсер: `applyServerEvent` плюс «мои заказы» (флаг `mine` в событиях всегда `false`)            |
| `search-controller.ts`, `use-track-search.ts` | дебаунс 260 мс, отмена через `AbortController`, кэш на минуту, повтор                             |
| `request-errors.ts`                           | разбор кодов ошибок API в понятные состояния и тексты                                             |
| `search-overlay.tsx`, `track-result.tsx`      | полноэкранный поиск, чипы подсказок, недавние, превью 30 с (`preview-player.ts`), транслитерация  |
| `request-sheet.tsx`                           | лист заказа: посвящение, заметка, заказ текстом, обратный отсчёт лимита                           |
| `my-requests-sheet.tsx`                       | «Мои заказы» с живыми статусами                                                                   |
| `use-mine-notifications.ts`                   | тост и вибрация, когда диджей принял, включил или отклонил ваш трек                               |
| `guest-app.tsx`                               | сборка экрана, состояния «диджея нет», «заказы закрыты», «пауза между треками»                    |

Как ведёт себя клиент:

- **Токен.** `deviceId` (UUID) хранится в `localStorage` под `jm:device-id`, при недоступном хранилище в памяти. Сессия гостя (`jm:guest:<slug>`) переиспользуется до истечения (`exp` читается из JWT, запас 2 минуты). Запрос с 401 один раз обновляет токен и повторяется.
- **QR.** Параметр `?t=` запоминается (`jm:table:<slug>`), а из адреса убирается после входа, поэтому перезагрузка страницы не накручивает счётчик сканов. Токен стола уходит в `guestJoin` только при новом скане, а в каждый заказ добавляется для аналитики по столам.
- **Время.** Прогресс трека считается по серверным часам: сдвиг берётся как максимум по последним шести образцам (`serverTime` минус время получения, задержка сети только уменьшает оценку). Экран поэтому не «убегает» от телефона с неверным временем.
- **Связь.** При обрыве `createRealtimeClient` переподключается с задержкой и присылает `resync`. Плюс `online` и `visibilitychange` перезапускают подключение. Плашка «нет связи» появляется через 2,5 секунды простоя, чтобы не мигать. Заказы, сделанные до обрыва, подтягиваются заново из `requestsMine` после каждого снимка.
- **Приватность.** Заметки и посвящения других гостей приходят от сервера как `null` для заказов в статусе `pending` (`docs/API.md`, «Видимость данных»). Клиент ничего не «достраивает»: свою заметку хранит из ответа `requestCreate`.
- **Тексты.** Три языка в `lib/messages.ts`: узбекский (латиница, с апострофом `ʻ`), русский, английский. Язык выбирается так: cookie `jm-locale`, затем `Accept-Language`, затем `defaultLocale` заведения. Выбор гостя пишется в cookie и `localStorage`, так что сервер рендерит уже нужный язык.

### Экран ТВ (`src/tv`)

Сцена фиксированного размера 1920×1080 масштабируется в любой экран (`--tv-scale` выставляется инлайн-скриптом до первого кадра). Режимы:

- **играет**: герой с обложкой, QR в белой карточке, две ближайшие заявки, панель посвящений, бегущая строка;
- **пауза** (сессия идёт, трека нет): анимированный градиент, визуализатор на CSS и крупный призыв «Выбирайте музыку сами»;
- **диджея нет**: тот же фон и QR, текст «Диджей скоро начнёт».

Параметры адреса: `?theme=club|lounge|cafe` и `?locale=uz|ru|en`. Без `locale` берётся язык заведения (ТВ не знает языка зала). Курсор скрыт, всё содержимое медленно дрейфует на ±5 px в цикле 7 минут (защита от выгорания). Снимок состояния обновляется раз в минуту и по событиям. Показываются только данные, которые сервер отдаёт роли `tv`: названия треков, посвящения принятых заказов, число голосов. QR рисуется на сервере через `@joymusic/qr` (`renderJoyCode`, логотип из `@joymusic/brand`) и кодирует `${origin}/v/${slug}`.

## PWA

- **Манифест** свой у каждого заведения: имя, тема (`theme_color` и `background_color` берут холст темы), `start_url=/v/<slug>?source=pwa`, `scope=/v/<slug>`, иконки 192, 512 и maskable из `@joymusic/brand/assets/pwa`.
- **Service worker** (`public/sw.js`, регистрируется только в production после `load`). Навигации идут сетью с таймаутом 4 секунды, страницы `/v/*` кладутся в кэш (не больше 8) и отдаются, если сети нет. Если нет и кэша, показывается `offline.html`. Статика (`/_next/static`, шрифты, обложки `/art`) работает по схеме stale-while-revalidate, не больше 160 записей. Никогда не кэшируются: другие origin (то есть API и WebSocket), `/v1/*`, `/api/*`, `/tv/*`, манифесты.
- **Подсказка «добавить на экран»** появляется не сразу: после первого заказа или голоса либо с третьего визита, только там, где есть `beforeinstallprompt` или iOS Safari (для iOS текст-инструкция). Закрытие запоминается на 14 дней.
- **Быстрый первый кадр.** Оболочка и первое состояние приходят с сервера HTML-ом. Клиент подгружает `@joymusic/shared` (zod, около 95 КБ gzip) уже после гидратации, лист заказа, «Мои заказы» и поиск грузятся по требованию. Обложки идут через `/art` в нужном размере (120 px для списков, 500 для героя). Шрифты (Manrope и Unbounded, latin) предзагружаются заголовком `Link`. Обложка героя видна до гидратации, а на первый вход в поиск уже прогреты чип-подсказки.

## Тесты

`pnpm --filter @joymusic/web test` (vitest, jsdom). Покрыто: хранилище сессии (вход, обновление, единый полёт, сбой `localStorage`), контроллер поиска (дебаунс, отмена, кэш, повтор), маппинг ошибок заказа, редьюсер живого состояния и «моих» заказов, оценка сдвига часов и прогресс по серверному времени, локаль и тема, транслитерация, недавние запросы, плеер превью, модель ТВ, а также компоненты: лист заказа (лимит с обратным отсчётом, `requests_closed`, `content_blocked`, сеть), поиск, «дальше в очереди», «Мои заказы».

### E2E (Playwright)

```sh
pnpm --filter @joymusic/web test:e2e
```

Playwright сам поднимает всё нужное (`playwright.config.ts`): локальные Postgres и Redis через `apps/api/scripts/test-services.mjs`, отдельную базу `joymusic_web_e2e` (пересоздаётся при каждом запуске, миграции и `db:seed`), API на `127.0.0.1:4410` и собранное приложение (`next build` в `dist/next-e2e`, `next start`) на `127.0.0.1:3100`. Порты меняются через `E2E_API_PORT` и `E2E_WEB_PORT`. Чтобы не пересобирать при отладке, поднимите серверы сами и запустите с `E2E_REUSE=1`. Chromium берётся из `PLAYWRIGHT_BROWSERS_PATH` (`/opt/pw-browsers`), скачивать ничего не нужно.

Сценарий сквозной: гость сканирует QR стола (счётчик сканов растёт на 1), видит «диджея нет», диджей (`dj@joymusic.uz` через REST) стартует сессию, страница и ТВ обновляются без перезагрузки, гость находит трек и заказывает с посвящением, диджей видит заметку, принимает и включает трек, гость и ТВ видят статусы и «играет сейчас». Дальше: второй гость заказывает тот же трек и получает голос (`merged`), голосование из списка, лимит заказов с обратным отсчётом, закрытие приёма, плашка «нет связи», переключение языка с сохранением, конец сессии, 404 для неизвестного заведения. Отдельные наборы: PWA (манифест, иконки, установка SW, офлайн-перезагрузка, отсутствие API в кэше) и ТВ (без полос прокрутки, курсор, масштаб, `?theme` и `?locale`, QR). Поиск в каталоге в e2e подменён перехватом запроса `catalogSearch` в браузере (Deezer может быть недоступен из CI), всё остальное идёт в живой API.

## Lighthouse

`node apps/web/scripts/lighthouse.mjs [url]` (Lighthouse 13, эмуляция мобильного, Chromium из Playwright) печатает баллы по трём прогонам и проверку установки PWA через CDP. Переменные: `RUNS`, `THROTTLING=devtools`, `SKIP_PWA=1`. Lighthouse 12 и новее убрал категорию PWA, поэтому её даёт `pnpm dlx lighthouse@11.7.1 <url> --only-categories=pwa`.

Замеры на production-сборке, мобильный профиль по умолчанию (медленная 4G, замедление CPU в 4 раза), на загруженной машине с общим процессором (несколько агентов работали параллельно), демо-заведение с играющим треком, очередью и 6 обложками.

| Экран                                     | Performance (5 прогонов) | Accessibility | Best practices | SEO | FCP   | LCP       | TBT        |
| ----------------------------------------- | ------------------------ | ------------- | -------------- | --- | ----- | --------- | ---------- |
| Ожидание диджея (`/v/cafe-nur`)           | медиана 90 (87 до 92)    | 100           | 100            | 60  | 0.9 с | 2.7-2.9 с | 230-380 мс |
| Играет трек, очередь (`/v/joy-demo-club`) | медиана 81 (73 до 85)    | 100           | 100            | 63  | 1.2 с | 4.0-4.2 с | 180-580 мс |

PWA (Lighthouse 11.7.1, категория PWA): 100. Проходят `installable-manifest`, `splash-screen`, `themed-omnibox`, `content-width`, `viewport`, `maskable-icon`. Через CDP `Page.getInstallabilityErrors` ошибок установки нет, Service Worker управляет страницей, перезагрузка без сети рисует приложение.

Как читать цифры:

- Категория SEO ниже 100 намеренно: страницы заведений закрыты от индексации (`noindex`), это гостевой QR-адрес, а не сайт.
- Экран с играющим треком не дотягивает до 90 из-за LCP. LCP здесь обложка героя (272 px, 64 КБ), а симулятор Lighthouse делит канал 1,6 Мбит/с между обложкой и 280 КБ JS, шрифтами и документом. Тот же экран в настоящем Chromium с теми же ограничениями сети и CPU (`Network.emulateNetworkConditions` 1,6 Мбит/с, 150 мс, замедление CPU в 4 раза) даёт FCP 1,1 с и LCP 2,1 с, то есть попадает в зелёную зону (менее 2,5 с). В режиме `THROTTLING=devtools` Lighthouse показывает 82-84 для играющего экрана и 88-90 для ожидания.
- Разброс TBT в основном шум: на машине параллельно работали другие процессы (load average до 7).

Что было сделано для скорости: HTML от сервера с первым состоянием, `@joymusic/shared` (zod) грузится после гидратации и не мешает первому кадру, листы и поиск подгружаются по требованию, чанк поиска и подсказки прогреваются в простое, обложки очереди это лёгкие `<img>` без SVG-заглушки, шум и `mix-blend` фона отключены (`grain={false}`), очередь дорисовывается через 2 секунды, шрифты и обложка героя предзагружаются, обложка видна до гидратации. Что ещё дало бы выигрыш: убрать `motion` из героя (в `NowPlayingHero` он нужен для наклона обложки, около 45 КБ gzip) и отдавать обложки через свой CDN.

## Что добавлено в контракт и что осталось

- В `packages/shared/package.json` добавлен `"sideEffects": false`. Без него сборщик не выбрасывает неиспользуемые модули barrel-файла и тянет в основной бандл гостя все схемы zod. Кода в пакете это не меняет.
- Прокси `/art` и оценка сдвига часов живут в веб-приложении, в контракт не попали.
- Известные ограничения: предпрослушивание в каталоге зависит от `previewUrl` (Deezer отдаёт токенизированные ссылки с ограниченным сроком, после протухания кнопка молча сбрасывается); плитка «Поделиться» для iOS без `beforeinstallprompt` показывает только подсказку, нативного диалога установки там нет; ТВ не переключает тему по времени суток, тема берётся от заведения или из `?theme`.
