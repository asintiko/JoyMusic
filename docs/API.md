# API (`@joymusic/api`)

Fastify 5, Postgres (Drizzle), Redis (необязателен), WebSocket. Контракт маршрутов, событий и схем живёт в `packages/shared` (`routes`, `realtime.ts`, `venue-state.ts`). Сервер валидирует вход по тем же Zod-схемам, что и клиенты. Вне production сервер ещё и проверяет свои ответы по схеме.

## Переменные окружения

Шаблон лежит в `apps/api/.env.example`. Обязательны `DATABASE_URL`, `JWT_SECRET` (не короче 32 символов) и `PUBLIC_WEB_URL`.

## Запуск локально

```sh
node apps/api/scripts/test-services.mjs start
cp apps/api/.env.example apps/api/.env
pnpm --filter @joymusic/api db:migrate
pnpm --filter @joymusic/api db:seed
pnpm --filter @joymusic/api dev
```

`test-services.mjs` поднимает локальные Postgres (порт 54329, базы `joymusic_test` и `joymusic_dev`) и Redis (порт 6390) без Docker. Он же используется тестами. Остановка: `node apps/api/scripts/test-services.mjs stop`.

Проверки:

```sh
pnpm --filter @joymusic/api typecheck
pnpm --filter @joymusic/api lint
pnpm --filter @joymusic/api test
```

Сборка и запуск: `pnpm --filter @joymusic/api build && pnpm --filter @joymusic/api start`.

## Авторизация

Все защищённые запросы несут `Authorization: Bearer <token>`.

### Гость

1. `POST /v1/venues/:slug/guest` с необязательными `deviceId` (8-64 символа, клиент хранит его в `localStorage`), `tableToken` (параметр `t` из QR) и `locale`.
2. Ответ: `guestToken` (JWT, живёт 12 часов, привязан к заведению), `deviceId`, `tableLabel`. Если `tableToken` найден и активен, счётчик сканов QR растёт на 1. Заблокированное устройство получает `403 forbidden`.
3. Маршруты с `auth: "guest"` (`requestCreate`, `requestVote`, `requestsMine`) требуют этот токен. Токен другого заведения даёт `403`.
4. Публичные маршруты (`venueState`, `catalogSearch`, `suggestions`) принимают токен необязательно. С токеном `mine` в состоянии заполняется для устройства гостя.

### Диджей и администратор

- `POST /v1/auth/register`, `POST /v1/auth/login`, `POST /v1/auth/google`, `POST /v1/auth/invites/accept` возвращают `accessToken` (15 минут), `refreshToken` (30 дней) и `me`.
- `POST /v1/auth/refresh` обменивает refresh на новую пару. Refresh-токены ротируются, повторное использование старого отзывает всё семейство.
- `POST /v1/auth/logout` отзывает refresh-токен.
- Несколько организаций: заголовок `X-Organization-Id` выбирает контекст для админских маршрутов.
- Вход по паролю блокируется после `LOGIN_MAX_FAILURES` неудач подряд на пару email+IP (`429`).

### Десктоп: OAuth PKCE через системный браузер

1. Приложение генерирует `codeVerifier` (43-128 символов `[A-Za-z0-9-._~]`), считает `codeChallenge = base64url(SHA256(codeVerifier))` и случайный `state`.
2. Открывает в браузере страницу входа веб-приложения с `codeChallenge` и `state`.
3. Веб, уже имея сессию пользователя, вызывает `POST /v1/auth/desktop/authorize` (`auth: user`) с `codeChallenge` и `state` и получает одноразовый `code` (живёт 60 секунд).
4. Браузер открывает `joymusic://auth?code=...&state=...`. Приложение сверяет `state`.
5. Приложение вызывает `POST /v1/auth/desktop/token` с `code` и `codeVerifier` и получает то же, что при входе (`accessToken`, `refreshToken`, `me`). Код одноразовый и привязан к challenge.

## Жизненный цикл заказа

```
гость создаёт заказ
        |
        v
   +---------+  голос других гостей (votes +1, один голос на устройство)
   | pending |<---------------------------------------------------+
   +---------+                                                    |
     |   |   \                                                    |
     |   |    +--(45 минут без решения)--------------> expired    |
     |   +--(DJ decline, reason)-------------------> declined ----+ (DJ может принять снова)
     |                                                  ^
     +--(DJ accept, position = max + 1)--> accepted ----+ (DJ decline)
     |                                        |
     |                                        +--(DJ play)--+
     +--(DJ play)-------------------------------------------+
                                                           v
                                                       playing  --(DJ played / следующий трек / clear)--> played
                                                           |
                                            конец сессии: все открытые заказы -> expired
```

- Дубликат в окне `duplicateWindowMinutes` (тот же `trackId` или тот же нормализованный `artist`+`title` среди открытых заказов сессии) не создаёт новый заказ: гость голосует за существующий (`merged: true`, HTTP 200). Повторный голос того же устройства даёт `409 conflict`. Если совпадение уже играет, голос не добавляется.
- Лимит `maxRequestsPerDevice` за `windowMinutes` считает только новые заказы. Голос за дубликат в лимит не входит.
- Порядок проверок при создании: устройство не заблокировано, `requests_closed`, `no_active_session`, `notes_disabled`, `free_text_disabled`, `content_blocked`, дубликат (голос), `request_limit_reached`.
- `djQueueAdd` создаёт заказ сразу в статусе `accepted` без лимитов и фильтров. `deviceId` такого заказа `dj:<userId>`.
- `djNowPlayingSet` сопоставляет трек с принятым заказом сессии по нормализованным артисту и названию (скобки и `feat.` отбрасываются, артисты сравниваются по вхождению). Найденный заказ становится `playing`, предыдущий `playing` становится `played`. Повторная отправка того же трека обновляет BPM, тональность и длительность без нового события, если ничего не изменилось. Так безопасно слать состояние из софта диджея каждые несколько секунд.
- Все изменения идут в одной транзакции под advisory-локом заведения. События публикуются после коммита.

## Видимость данных

- `note` и `dedicatedTo` видит диджей (`djSessionState`, WebSocket с `role=dj`), а также автор заказа в `requestCreate` и `requestsMine`.
- Для гостей и ТВ (`venueState`, WebSocket с `role=guest|tv`) эти поля равны `null` у всех заказов, кроме `accepted`, `playing`, `played`. В `nowPlaying.dedicatedTo` посвящение показывается, потому что трек уже играет.
- Гость, проголосовавший за чужой заказ, получает его без заметки (`requestVote`, `requestsMine`).
- `mine` в широковещательных событиях всегда `false`. В снимке и в HTTP-ответах он считается по устройству, если передан гостевой токен. Клиент помечает свои заказы по `requestsMine` и по ответам своих запросов.
- `tableLabel` виден всем.

## Realtime

Адрес: `GET /v1/ws?venue=<slug>&role=guest|dj|tv&token=<jwt>` (схема `realtimeQuerySchema`, роль по умолчанию `guest`).

Проверки выполняются до апгрейда, ошибка приходит обычным HTTP-ответом с JSON-телом:

| Условие                                                    | Статус |
| ---------------------------------------------------------- | ------ |
| `Origin` есть, но его нет в `CORS_ORIGINS`                 | 403    |
| неверные query-параметры (например, неизвестная `role`)    | 400    |
| заведение не найдено                                       | 404    |
| `role=dj` без токена или с неверным/гостевым токеном       | 401    |
| `role=dj`, пользователь не состоит в организации заведения | 404    |
| превышено `WS_MAX_CONNECTIONS_PER_IP`                      | 429    |

Клиентам без заголовка `Origin` (десктоп, серверные скрипты) проверка origin не применяется. `guest` и `tv` могут подключаться анонимно. Некорректный или чужой гостевой токен не отклоняется, соединение становится анонимным.

### Порядок сообщений

1. Сразу после подключения приходит `state.snapshot` (`seq` в конверте равен `data.seq`). Снимок фильтруется по аудитории.
2. Далее события `nowplaying.updated`, `request.upserted`, `request.removed`, `queue.reordered`, `settings.updated`, `session.changed`. `seq` растёт на 1 внутри заведения. Пропуск (`seq > lastSeq + 1`) означает потерю: клиент шлёт `resync`.
3. События, пришедшие во время построения снимка, буферизуются и отправляются после него, если их `seq` больше снимка.

Клиентские сообщения (JSON, текстовые кадры):

- `{"type":"ping"}` -> `{"type":"pong","serverTime":"..."}`
- `{"type":"resync","lastSeq":N}` -> новый `state.snapshot`, если `N` не равен текущему `seq` заведения. Если клиент актуален, ответа нет.

Порядок событий для типовых действий:

| Действие              | События (по порядку)                                                                                                              |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| старт сессии          | `session.changed`                                                                                                                 |
| новый заказ или голос | `request.upserted` (pending)                                                                                                      |
| accept / decline      | `request.upserted`                                                                                                                |
| play                  | `request.upserted` (предыдущий, если был, `played`), `request.upserted` (`playing`), `nowplaying.updated`                         |
| played текущего       | `request.upserted` (`played`), `nowplaying.updated` (null)                                                                        |
| `djNowPlayingSet`     | `request.upserted` (прошлый `played` и связанный `playing`), `nowplaying.updated`                                                 |
| `djNowPlayingClear`   | `request.upserted` (`played`), `nowplaying.updated` (null)                                                                        |
| reorder               | `queue.reordered` (полный порядок принятых заказов)                                                                               |
| настройки             | `settings.updated`                                                                                                                |
| конец сессии          | `request.upserted` (`expired`) на каждый открытый заказ, `nowplaying.updated` (null) если что-то играло, `session.changed` (null) |
| фоновое истечение     | `request.upserted` (`expired`)                                                                                                    |

Заказы в статусах `declined` и `expired` тоже считаются закрытыми: гостям и ТВ они приходят без `note` и `dedicatedTo`.

### Устойчивость

- Один pub/sub-канал на заведение (`venue:<id>`), подписка создаётся при первом клиенте и снимается с последним. С `REDIS_URL` события идут через Redis и доходят до клиентов на других экземплярах. Без Redis всё работает в памяти процесса.
- `seq` берётся атомарно (`INCR`) и публикуется по одному за раз на заведение, порядок внутри экземпляра сохраняется.
- Медленный клиент (буфер отправки больше `WS_MAX_BUFFERED_BYTES`) обрывается. Клиент без ответа на ping закрывается.
- Закрытие кодами: 1003 (бинарные кадры), 1008 (больше 30 сообщений за 10 секунд или больше 10 невалидных сообщений), 1009 (превышен размер), 1011 (ошибка сервера), 1001 (остановка сервера).
- Права диджея проверяются при подключении. Просроченный access token уже открытое соединение не рвёт.

## Фоновые задачи

Планировщик на `setInterval` (таймер `unref`, останавливается при закрытии приложения, безопасен для нескольких экземпляров: обновления условные).

- `expire-pending-requests`: заказы `pending` старше `REQUEST_EXPIRY_MINUTES` (45) получают `expired`, публикуется `request.upserted`.
- `end-abandoned-sessions`: активные сессии, в которых дольше `SESSION_IDLE_HOURS` (18) не было ни заказов, ни треков, завершаются как обычным `djSessionEnd`.

Простой считается от последней активности: старт сессии, обновление любого заказа, начало трека. `djSessionStart` завершает такие сессии этого заведения перед проверкой на конфликт.

## Каталог и подсказки

- `GET /v1/catalog/search?q=&limit=` идёт через `@joymusic/catalog` (Deezer и iTunes, транслитерация, кэш в Redis при наличии). Маршрут публичный, лимит `RATE_LIMIT_SEARCH_MAX` в минуту. Недоступность каталога даёт `503`.
- `GET /v1/venues/:slug/suggestions` всегда возвращает 7 секций. `trending_here` считается по заказам заведения за 14 дней, `dj_picks` по самым принятым и сыгранным трекам последнего диджея заведения, остальные берутся из каталога. Если данных мало, секция добирается из каталога, а в крайнем случае из последних известных треков. Ответ кэшируется на 2 минуты.
- Трек из каталога сохраняется в таблицу `tracks` при создании заказа. Если клиент прислал `track`, сервер перепроверяет его по каталогу (`getTrack`) и хранит канонические данные. Если каталог не ответил и трека нет в базе, заказ создаётся как свободный текст.

## Коды ошибок

Тело ошибки: `{"error":{"code","message","details?"}}`.

| code                    | HTTP | Когда                                                                                           |
| ----------------------- | ---- | ----------------------------------------------------------------------------------------------- |
| `validation_failed`     | 400  | тело, query или params не прошли схему, битый JSON, неверный порядок очереди                    |
| `unauthorized`          | 401  | нет или просрочен токен                                                                         |
| `forbidden`             | 403  | нет прав, устройство заблокировано, токен чужого заведения, недопустимый origin                 |
| `not_found`             | 404  | нет заведения, заказа, трека, сессии. Чужая организация тоже даёт 404                           |
| `conflict`              | 409  | другой диджей уже ведёт сессию, повторный голос, недопустимый переход статуса, сессия завершена |
| `rate_limited`          | 429  | лимиты запросов, входа, WebSocket. Есть `retry-after`                                           |
| `requests_closed`       | 403  | `requestsOpen = false`                                                                          |
| `request_limit_reached` | 429  | лимит заказов устройства. В `details`: `limit`, `windowMinutes`, `retryAfterSeconds`            |
| `track_required`        | 400  | зарезервирован в контракте (сервер отдаёт `validation_failed` для пустого заказа)               |
| `free_text_disabled`    | 403  | заказ текстом при `allowFreeText = false`                                                       |
| `notes_disabled`        | 403  | заметка или посвящение при `allowNotes = false`                                                 |
| `content_blocked`       | 422  | запрещённые слова. В `details.field` указано поле                                               |
| `no_active_session`     | 409  | диджей не начал сессию                                                                          |
| `invalid_credentials`   | 401  | неверный email или пароль                                                                       |
| `email_taken`           | 409  | email уже зарегистрирован                                                                       |
| `invite_invalid`        | 400  | приглашение неверно или истекло                                                                 |
| `internal`              | 500  | ошибка сервера. 503 для недоступной базы или каталога                                           |

## Фильтр запрещённых слов

Проверяются `note`, `dedicatedTo`, свободный текст (`artist`, `title`) и, если трек не удалось подтвердить в каталоге, его название. Названия проверенных треков каталога не фильтруются.

Текст нормализуется: регистр, диакритика, повторы букв (`fuuuck`), разделители (`f.u.c.k`), подмена кириллицы и латиницы (`fuсk` с русской `с`), цифры и символы вместо букв (`sh1t`), транслитерация кириллицы (`хуй` совпадает с `xuy`). Список состоит из встроенных корней (русский, узбекский латиницей и кириллицей, английский) и слов организации из `adminBannedWords`. Встроенные корни совпадают с началом слова, чтобы ловить формы слова и не срабатывать на середину чужих слов.
